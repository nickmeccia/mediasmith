After using Mediasmith for a while, I have a few complaints against my design:
• Needing to navigate into details view to execute any action is annoying:
  • There is a <1s delay when entering details view, and entering for many files in a session is time that adds up
  • The extra keystrokes of "ent" and "esc" to enter and exit details view also add up during a session
  • Plus, the extra keystrokes don't connect to my mental model of what I'm doing--I visualize them almost as keys modifying the actiom I intend, instead of representing actions that I want to take

As a result, I want to change the mental model from "move focus between tree view and details view" to "move focus along a path."

Legend:
█ (mockup) = #ffa62b PRIMARY bg color (TUI) = focusable element, currently focused
▒ (mockup) = #474747 GREY_30 bg color (TUI) = focusable element, currently unfocused
- (mockup) = #e2e2e2 GREY_30 fg color when unfocused, #ffa62b PRIMARY fg color when connecting focused elements (TUI) = path connecting focusable elements
░ (mockup) = #ffa62b PRIMARY fg color (TUI) = action available regardless of focus
═ (mockup) = viewport width


Rules:
• Focus is represented by #orange bg color behind one single element at a time
• If this element is editable, it is the only element able to be edited while focused
• The user is able to move focus to adjacent focusable elements with the arrow keys
• Adjacency is imdicated by box-drawing characters connecting the elements
_ Unfocused, focusable elemnents are indicated by a #grey background color
• From each focusable element, a variety of actions are available, indicated by #orange fg text. This text is not necessarily connected to or adjacent to the currently-focused element, and may appear anywhere in the UI.

Mockup notes:
• Layer 1: Background Color
  • Mockups 1-3 combine to form one mockup
  • This mockup depicts bg color of cells
  • █ = #ffa62b PRIMARY bg color (TUI) = focusable element, currently focused
  • ▒ = #474747 GREY_30 bg color (TUI) = focusable element, currently unfocused
  • The unicode box-drawing characters connecting the node in the filetree with the file's details in the right pane follow the same logic as the box-drawing characters in the file tree:
    • GREY_30 when a tree node is focused
    • PRIMARY when a file input or file button is focused
    • Draw line of focus to that file (see "Author Input Selected" mockup and its notes for more information)
• Layer 2: Foreground Content
  • Mockups 1-3 combine to form one mockup
  • This mockup depicts fg content with no color information
  • If user presses right arrow or ENT on a file node, filename field becomes selected
  • Down & up arrow keys traverse input fieldss as they currently do, selecting adjacent fields
  • However, down & up arrow keys traverse button BARS instead of buttons
    • Example:
      • ^x Cut is focused
      • User presses down arrow
      • ^1 Folderize becomes focused
      • User presses down arrow
      • Nothing happens
      • User presses right arrow
      • ^2 Split Omnibus becomes focused
  • Behavior of right arrow and ENT on a folder node is unchanged:
    • Right arrow expands node
    • ENT moves focus to filename input
• Layer 3: Foreground Color
  • Mockups 1-3 combine to form one mockup
  • This mockup depicts fg color
  • ░ = #ffa62b PRIMARY fg color (TUI) = action available regardless of focus
  • So, this is change that this UI revision is built around: the ability for the user to perform actions on a given file without needing to "enter" details view.
• Alternate Content Example
  • Example depicting path character intersecting with file details at a higher Y position than other examples
  • Between the two examples, you should conclude:
    • Path characters extend outward from file in tree until they reach the gutter between file tree and file details
    • Path characters are the drawn to connect to all focusable fields

  • When there are too many buttons to fit in one line of button bar, overflow buttons into a new button bar, as seen in this example

    • ESC Exit

  • When a node has unsaved changes, the contextual button bar changes:
    • ^s Save
    • ESC Discard & Exit

Consequences:
• Path Input
  • Add the `^/` keybinding before the input in the PRIMARY color
  • Replace with `ESC` keybinding when this element has focus
  • So, this means there needs to be an extra space after the `^/` keybinding, so that it's really three characters (`^/ `), so that `ESC` will fit
• File Tree
  • No change to colorization of box drawing characters depicting folder nesting
  • All unfocused nodes gain the background color GREY_30
• Button Bars
  • Separate button bar into 3 button bars (examples only, not exhaustive lists):
    • "Contextual" button bar:
      • Save
      • Exit
      • Discard & Exit
    • "File" button bar:
      • Open
      • Cut
      • Copy
      • Delete
    • "Actions" button bar:
      • Folderize
      • Split Omnibus
      • Convert to Mobi
      • Convert to AZW3
      • Write OPF
      • Clean
      • Upload Cover
      • Extract Cover
  • In the filetype button bar, remove keybindings within button names. Example:
    ^3 fetch s^ubtitles <- before
    ^3 fetch subtitles <- after
    Explanation: there are way too many keybindings to memorize at this point, and it's easier to just note the position of the button ("3rd in a list," for example) than it is to identify which letter of a command is the keybinding (for example, `^u` is "fetch subtitles", which is a weird letter to represent this command)
  • Capitalize button names
    • See mockups for examples
    • Explanation: since keybindings are no longer inline with button text, button text can contain capital letters
• Scrollbars
  • From an HTML/CSS point of view, I am imagining that the viewport is now constructed like this:
    • "Details view":
      • Has its own scroll container
      • Position is fixed to top of viewport and unaffected by directory tree scrolling
    • "Directory tree":
      • Scroll container now spans the full viewport
      • Scrollbar appears at right edge of the viewport
      • Scrolls only the tree content, because file details are fixed position and removed from the flow
  • Here is the same idea expressed as a diagram
    ┌────────────────────────────────────────────────┐
    │ ┌─────────────────┐      ┌─────────────────┐   │
    │ │ Path Input      │      │ File inputs    ▌│   │
    │ └─────────────────┘      │ Button bars     │   │
    │  directory tree          │ position:fixed  │ ▌ │
    │  ╰─ node                 └─────────────────┘   │
    │  ▂▂▂▂▂▂▂▂▂▂                                    │
    └────────────────────────────────────────────────┘
    ▂ = horizontal scrollbar
    ▌ = vertical scrollbar
